# 임베딩 모델 파인튜닝 랩 — 프로젝트 보고

- **작성일**: 2026-07-11
- **프로젝트**: RAG Embedding Lab (사내 사이트 검색용 임베딩 모델 파인튜닝·평가·서빙 파이프라인)
- **현재 상태**: 데이터 → 학습 → 평가 → 비교 → 납품 → 서빙까지 전 구간 구축 완료, PoC 데이터로 end-to-end 검증 완료

---

## 1. 요약 (Executive Summary)

사내 사이트 검색의 **의미 검색(dense) 부품을 우리 데이터로 파인튜닝해 교체**하기 위한
실험·검증 인프라를 구축했습니다. 핵심 성과는 세 가지입니다.

1. **전 과정 파이프라인 완성** — 학습 데이터 생성부터 모델 학습, 통계 검정 기반 비교,
   납품 패키징, 그리고 실제 벡터 DB(Qdrant) 서빙까지 웹 UI 하나에서 끝나는 구조.
2. **결과의 신뢰성을 구조적으로 보장** — 평가셋 지문(fingerprint) 강제, dev/final 분리,
   쿼리별 유의성 검정(p값), 서빙 패리티 계약 등 "좋아 보이는 숫자"가 아니라
   "믿을 수 있는 숫자"만 나오도록 설계.
3. **서빙 절차의 자동화** — 모델 교체에 필수인 전면 재색인을 무중단(blue-green)·멱등으로
   구현하고, 모델 납품(핸드오프) 시 자동 실행되도록 연결. 재색인·검색을 실물로 확인하는
   검색 플레이그라운드 포함.
4. **모델 중립 비교 인프라** — 입력 포맷을 모델별 프로파일로 추상화해 Qwen3-0.6B와
   Nemotron-3-Embed-1B를 같은 레시피로 학습·비교. 정확도뿐 아니라 응답속도·GPU·저장비용을
   실제 서빙 경로에서 측정(`rag-bench`)해 "실질적 서비스 조건"의 트레이드오프를 수치화(3.6).
5. **하이브리드·정성 근거** — dense와 BM25를 RRF로 실제 융합해 "파인튜닝이 은어를 열고
   그 위에서 어휘 융합이 순위를 다듬는다"는 2×2를 수치로 보였고(3.7), 파인튜닝 전후 랭킹을
   쿼리 단위로 비교해 "틀린 시스템→정답 시스템"으로 뒤집힌 사례를 표로 정리(3.8) — 집계
   숫자를 이해관계자가 눈으로 확인할 수 있는 근거로 보강.

PoC 데이터(공공 사이트 크롤 1,500문서)에서 파이프라인 전체가 정상 동작함을 확인했습니다.
파인튜닝 수치 개선 폭은 PoC 데이터 특성상 제한적이며(3절), **실사용 검색 로그 확보가
다음 단계의 핵심**입니다.

## 2. 배경 — 왜 임베딩 파인튜닝인가

### 2.1 문제

사내 검색 프로덕션은 BM25(키워드) + Dense 임베딩(의미) + 리랭커의 3단 하이브리드로
운영 중입니다. 이 중 dense 부품은 공개 임베딩 모델을 그대로 쓰고 있는데, 공개 모델은
일반 한국어는 잘 알지만 **우리 조직의 언어를 모릅니다** — 사내 시스템 이름, 약어, 신조어,
"그 업무를 우리가 부르는 말"과 실제 문서를 연결하지 못합니다.

### 2.2 파인튜닝으로 얻는 것

| 이점 | 설명 |
|---|---|
| **도메인 어휘 정렬** | (실제 쿼리, 정답 문서) 쌍 수천 개로 임베딩 좌표계를 재배치 — 사내 표현과 사내 문서가 가까워짐. 검색 품질 개선이 곧 RAG 답변 품질 개선으로 직결 |
| **낮은 데이터 비용** | 주력 학습법(MNRL)은 오답 라벨링이 불필요 — (쿼리, 정답) 쌍만 있으면 batch 내에서 오답을 자동 생성. 검색 클릭 로그를 그대로 학습 데이터로 전환 가능 |
| **부품 교체식 개선** | 검색 시스템을 새로 만드는 것이 아니라, 돌아가는 파이프라인의 부품 하나만 더 좋은 것으로 교체 — 리스크와 배포 범위가 작음 |
| **추론 비용 절감 옵션** | Matryoshka 학습 지원 — 한 모델로 1024/512/256차원 벡터를 겸용, 저장·검색 비용을 품질 손실 곡선을 보고 선택 가능 |
| **자산화** | 모델·레시피·평가 이력이 전부 기록으로 남아, 사람이 바뀌어도 재현·개선 가능한 조직 자산이 됨 |

임베더의 임무는 "정답을 1등으로"가 아니라 **"정답을 상위 후보(K=50)에 넣기"**입니다 —
순서는 뒤의 리랭커가 정리합니다. 반대로 임베더가 후보에 못 넣은 정답은 리랭커도 영영 볼 수
없으므로, **recall@K가 전체 검색 품질의 천장**이고 이것이 이 랩의 주 지표입니다.

## 3. 추진 경과 — 무엇을 만들었고 무엇을 확인했나

### 3.1 시스템 구성 (6단계 파이프라인, 웹 UI)

```
데이터 → 학습 → 평가 → 실험(비교) → 모델(납품) → 검색(서빙)
```

| 단계 | 내용 |
|---|---|
| **데이터** | 사이트 크롤로 corpus 구축 + 학습쌍 생성 3경로(실사용 로그 가져오기 / LLM 합성 — 검색창 스타일 쿼리 + 라운드트립 품질 필터 + 마진 가드 오답 채굴 / 직접 라벨링). 평가셋(BEIR 표준)은 학습 데이터와 문서 단위로 분리 |
| **학습** | Qwen3-Embedding-0.6B를 base로 4종 loss(MNRL/Cached/GIST/Triplet) + Full/LoRA + Matryoshka 지원. 매 epoch 검증 + early stopping으로 최적 시점 자동 저장. 하이퍼파라미터 스윕(중간 성적 기반 조기 탈락 포함) |
| **평가** | recall@1~50 · nDCG@10 · MRR@10, 95% 신뢰구간 동봉. 모든 점수에 평가셋 지문이 박혀 다른 시험지끼리 비교가 차단됨 |
| **실험** | 모델 간 쿼리별 diff + paired 순열 검정 p값 — "0.01 올랐다"가 아니라 "우연일 확률 x%"로 판정. dev로 선택, final은 승자 1회 확정 (선택 편향 차단) |
| **모델** | 전체 레시피(train_meta.json) 열람·보관, 핸드오프 패키지 납품 — 임베딩 계약(쿼리 포맷·풀링·정규화) + 패리티 검증 벡터(cosine ≥ 0.999) 동봉 |
| **검색** | Qdrant 벡터 DB 서빙 — 아래 3.3 |

### 3.2 PoC 데이터셋과 측정 결과

사내 데이터 확보 전, 공공 포털(korea.kr) 크롤을 사내 사이트의 대역으로 사용해
파이프라인 전체를 검증했습니다.

- **corpus**: 1,500 문서 (페이지 단위) / **학습쌍**: 791 (LLM 합성 쿼리) / **평가**: dev 224 쿼리

| 지표 (dev, 동일 평가셋) | base (Qwen3-0.6B) | 파인튜닝 (MNRL) | Δ |
|---|---|---|---|
| recall@1 | 0.799 | 0.808 | +0.9pp |
| nDCG@10 | 0.885 | 0.889 | +0.4pp |
| recall@50 | 0.982 | 0.982 | ±0 |

**정직한 해석**: 이 개선 폭은 신뢰구간이 겹치는 수준으로, 통계적으로 유의하지 않습니다.
원인은 파이프라인이 아니라 PoC 데이터의 특성입니다 — ① base 모델이 이미 잘 아는 공공
도메인 텍스트이고 ② 평가 쿼리가 LLM 합성이라 base 모델에 유리한 "표준적인" 표현 분포라서,
파인튜닝이 파고들 도메인 격차 자체가 작습니다. **파인튜닝의 이득은 base가 모르는 사내
용어·약어·실사용 표현에서 발생**하므로, 실데이터 적용 시 개선 폭이 커질 것으로 예상하며
그것이 4절의 1순위 과제입니다.

이번 PoC에서 얻은 방법론적 교훈도 기록해 둡니다: 초기 corpus 300문서에서는 상위 50 후보가
전체의 16%라 recall@50이 1.0에 포화되어 모델 변별이 불가능했고, corpus를 1,500으로 키워
지표가 비로소 모델을 가리기 시작했습니다. **평가 corpus 규모가 지표의 변별력을 결정**한다는
점은 사내 적용 시 평가셋 설계에 그대로 반영합니다.

### 3.3 서빙 경로 구축 (금주 완료)

모델을 "만드는 것"과 "실서비스에 올리는 것" 사이의 마지막 구간을 구현했습니다.

- **구성**: 임베딩 추론은 학습 산출물을 변환 없이 로드(sentence-transformers 인프로세스),
  벡터 검색은 Qdrant. 색인 문서와 검색 쿼리가 학습 때와 동일한 포맷 코드를 통과하도록
  강제(포맷 패리티) — 서빙에서 랩 점수가 증발하는 1순위 원인을 차단.
- **모델 교체 = 전면 재색인의 자동화**: 서로 다른 모델의 벡터는 호환되지 않으므로 모델
  교체 시 전 문서 재임베딩이 필수. 이를 (모델·차원·corpus 지문)별 버전 컬렉션 +
  alias 원자 전환으로 구현 — **무중단**(검색이 반쯤 만든 인덱스를 보는 순간이 없음),
  **롤백 가능**(옛 컬렉션 보관), **멱등**(같은 조건 재실행은 자동 스킵).
- **핸드오프 훅**: 모델 납품 시 그 모델로 재색인이 자동 시작 — "이 모델이 라이브로 간다"는
  결정을 인덱스가 사람 손 없이 따라감.
- **검색 플레이그라운드**: 웹 UI에서 인덱스 상태·재색인 진행률·실검색을 직접 확인.
- **검증**: 자동화 테스트 136건 통과. 실데이터 1,500문서 색인 후 실검색 end-to-end 확인
  (쿼리 임베딩 ~50ms, 최초 1회만 모델 로드 수 초).

이 서빙 경로는 프로덕션 대체가 아니라 **레퍼런스 구현**입니다 — 프로덕션이 dense 부품을
교체할 때 따라야 할 절차(전면 재색인 → 패리티 확인 → 무중단 전환 → 롤백 대비)를 랩 안에서
실제로 돌려 검증한 축소판이며, 납품받는 쪽의 절차서로 그대로 사용할 수 있습니다.

### 3.4 양성 대조군 실험 — 측정기 교정 완료 (7/18)

3.2의 정직한 해석("개선이 없는 건 데이터 탓")에는 검증되지 않은 전제가 있었습니다:
**격차가 있으면 이 파이프라인이 정말 잡아내는가?** 이를 확인하기 위해 실데이터
형태 — 실 운영 검색 컬렉션의 payload 스키마(site_id·url·version_name·title·
title_eng·llm_title·description·description_eng·user_queries·need_steps·
hard_guide_name) — 를 그대로 본뜬 가상 인트라넷 카탈로그(27개 사내 시스템,
195페이지)를 만들고, 도메인 격차를
설계로 주입했습니다 — 시스템마다 **사내 은어**(옛 시스템명·팀 별명)를 두되 은어는
문서 본문에 절대 등장하지 않고, 은어→시스템 연결은 클릭로그를 본뜬 학습쌍에만
존재합니다. base 모델이 은어 쿼리를 맞히는 것은 구조적으로 불가능하고, 파인튜닝만
배울 수 있는 상황입니다.

| dev 168쿼리 (nDCG@10) | base | 파인튜닝(MNRL) | Δ |
|---|---|---|---|
| 표준 쿼리 (n=82) | 0.986 | 0.991 | +0.005 (비회귀) |
| **은어 쿼리 (n=86)** | **0.152** | **0.772** | **+0.621** |
| 전체 | 0.559 | 0.879 | +0.320 (p=0.0001, 81승 1패 86무) |

은어 슬라이스의 recall@5는 0.17 → **0.99**로 회복됐고, held-out final 스플릿
1회 확정에서도 recall@5 1.0을 유지했습니다. **파이프라인은 도메인 격차가 있으면
잡아내고, 없으면(3.2) 없다고 말한다** — 측정기 교정이 끝났으므로, 실데이터에서
어떤 결과가 나오든 그 숫자를 신뢰할 수 있습니다.

이 실험은 지표 체계도 두 가지 업그레이드했습니다.

1. **슬라이스별 점수**: 전체 평균 0.559는 "표준 0.986 / 은어 0.152"의 이봉 분포를
   완전히 가렸습니다. 평가 쿼리에 슬라이스 태그(표준/은어 등)를 달면 평가·실험
   화면이 슬라이스별 점수를 함께 보여줍니다 — 실데이터에서도 쿼리 출처별(검색로그
   vs 신규 라벨링) 태그로 같은 장치를 씁니다.
2. **BM25 상보성(한계 기여)**: 내장 BM25 베이스라인과의 후보군 합집합 recall로
   "dense가 어휘 일치 위에 실제로 보태는 정답"을 측정합니다. base dense의 한계
   기여는 **+3%p**(표준 슬라이스에선 정확히 0 — BM25가 이미 다 잡음)였지만,
   파인튜닝 후 **+33%p**(은어 슬라이스 +64%p)로 뛰었습니다. dense 단독 점수가
   아니라 이 숫자가 프로덕션 하이브리드의 실제 개선 폭과 방향이 맞습니다.

### 3.5 클릭로그 노이즈 리허설 — 실로그 수용 준비 완료 (7/20)

실사용 로그(4절 1순위)는 그대로 쓰면 안 되는 데이터입니다 — 포지션 바이어스 클릭,
오클릭 바운스, 재검색, PII가 섞여 있습니다. 실데이터가 도착한 뒤에 정제 규칙을
만들면 늦으므로, 노이즈를 확률 모형으로 재현한 **모의 세션 로그(정답을 아는)**로
클리닝 계층을 미리 만들고 채점했습니다.

| 785 이벤트 → 학습쌍 | 라벨 정밀도 | 은어 표현 회수율 |
|---|---|---|
| 현행 방식 (클릭 1건 = 쌍 1건) | 0.590 | **0.000** |
| 클리닝 계층 통과 | **0.825** | **0.842** |

- **재검색 전이 규칙이 은어 supervision의 전부**입니다: 사내 은어 쿼리는 현행
  (어휘 일치) 엔진이 못 풀어 정답 클릭 자체가 없고 — 그래서 클릭만 봐서는 회수율
  0 — 사용자가 공식명으로 고쳐 검색해 성공한 세션의 **실패한 앞 쿼리를 최종 만족
  문서에 연결**해야 회수됩니다(끄면 0.842 → 0). 3.4에서 파인튜닝 이득의 원천이
  은어 연결임을 확인했으므로, 이 규칙이 실로그 가치의 핵심입니다.
- dwell 필터(20초 미만 = 바운스)를 끄면 정밀도 0.825 → 0.700으로 떨어집니다.
  남은 오염(~0.17)은 "오답 1등을 충분히 오래 본" 포지션 바이어스 클릭 — 세션
  구조만으로는 못 거르며, 대량 로그에선 (쿼리, 문서) 등장 횟수 집계(min_count)로
  희석합니다.
- 부산물: 만족 클릭 위에서 스킵된 문서가 hard negative로 자동 채굴되고(4절
  4순위 과제의 시작점), PII(이메일·전화번호) 쿼리는 학습 데이터에 들어가기 전에
  통째로 차단됩니다.
- 웹 UI의 데이터 탭 "실데이터 가져오기"에 **클릭로그(세션) 모드**가 추가됐습니다:
  원본 로그를 붙여넣으면 규칙별 처리 내역(직접/전이/바운스/PII)을 보여주고
  학습쌍으로 변환합니다. 실로그와 모의 로그가 같은 코드를 통과하므로, 데이터가
  도착하면 붙여넣는 것 외에 남은 작업이 없습니다.

**다운스트림 검증 — 클리닝이 라벨 지표만이 아니라 모델을 바꾼다.** 같은 로그에서
뽑은 두 학습셋으로 각각 파인튜닝해 dev(168쿼리)에서 비교했습니다:

| 로그만으로 학습 (nDCG@10) | 전체 | 은어 슬라이스 | 표준 슬라이스 | base 대비 p |
|---|---|---|---|---|
| base (학습 안 함) | 0.559 | 0.152 | 0.986 | — |
| naive 쌍 (클릭 1건=쌍 1건) | 0.555 | 0.183 | 0.945 | **0.72 (무의미)** |
| 클리닝 쌍 | **0.757** | **0.636** | 0.884 | **0.0001** |

- **naive 로그 학습은 통계적으로 '아무것도 안 한 것'과 구분되지 않습니다**
  (Δ −0.004, p=0.72) — 은어 supervision이 없고(회수 0) 노이즈만 배우다 1에폭에서
  조기 정체. 로그를 클릭 테이블로만 수집하면 이런 데이터가 됩니다.
- 클리닝 쌍 학습은 은어 recall@5를 0.17 → **0.90**으로 끌어올렸습니다(전이 쌍
  185건이 원천). 큐레이션 쌍 모델(nDCG 0.879)에는 못 미치고 표준 슬라이스가
  다소 물러나는(0.986→0.884) 라벨 노이즈 비용도 보입니다 — 실전 운용은 "로그
  단독 학습"이 아니라 **클리닝 쌍을 기존 학습셋에 증분 추가**하는 쪽입니다.

### 3.6 모델 비교 — Qwen3-0.6B vs Nemotron-3-Embed-1B (7/24)

랩이 한 모델(Qwen3-Embedding-0.6B)에 묶여 있으면 "이게 최선인가"에 답할 수 없습니다.
NVIDIA가 최근 공개한 Nemotron-3-Embed-1B(RTEB 1위 계열)를 **같은 레시피로 파인튜닝**해
정확도뿐 아니라 **응답속도·GPU·저장비용**까지 실제 서빙 경로에서 비교했습니다. 최종
목표가 "가장 좋은 모델로 서비스"인 이상, 정확도만의 비교로는 결정 근거가 되지 못합니다.

**입력 포맷 추상화(ModelProfile).** 두 모델은 입력 포맷이 다릅니다 — Qwen은 쿼리에
`Instruct: …\nQuery: …` 지시문을, Nemotron은 `query: ` / `passage: ` 접두사를 붙이고
차원(1024 vs 2048)·풀링(last-token vs 평균)도 다릅니다. 포맷을 틀리면 **예외 없이 점수만
조용히 나빠지므로**, 포맷을 모델별 `ModelProfile`로 한 곳(`core.formatting`)에 정의하고
학습·평가·서빙이 동일하게 참조하게 했습니다. 파인튜닝 산출물은 경로일 뿐 이름이 없어,
`train_meta.json`의 `base_model`로 포맷을 상속합니다. 이 추상화의 가치는 아래 ablation이
수치로 증명합니다.

**① 정확도 — 통계적으로 구분 불가 (dev 168쿼리, 동일 데이터·레시피).** 두 모델 모두
9에폭 실행 후 early stopping으로 6에폭을 저장했고, 짝지은 검정(paired permutation)으로
비교했습니다:

| nDCG@10 (dev) | dim | 전체 | 표준 | 은어 | recall@50 | Qwen 대비 p |
|---|---|---|---|---|---|---|
| Qwen3-0.6B FT | 1024 | 0.8794 | 0.9915 | 0.7725 | **1.0000** | — |
| Nemotron-1B FT | 2048 | **0.8885** | 0.9939 | 0.7879 | **1.0000** | 0.55 (무의미) |
| Nemotron-1B FT @1024 절단 | 1024 | 0.8548 | 0.9894 | 0.7265 | **1.0000** | 0.14 (무의미) |

- **파라미터·차원·디스크를 2배 쓰고도 held-out 정확도 차이는 유의하지 않습니다**(Δ+0.009,
  p=0.55). base 상태에선 오히려 Nemotron이 한국어 표준 쿼리에서 유의하게 뒤졌는데(p=0.001),
  파인튜닝 후 역전됐습니다 — **base 순위는 파인튜닝 후 순위를 예측하지 않습니다.**
- **저장비용을 맞추면(@1024 절단) 오히려 Qwen이 앞섭니다**(0.855 vs 0.879, 방향은 Qwen). 즉
  Nemotron의 근소한 우위는 순수하게 차원을 2배 쓴 대가였습니다.
- **recall@50은 세 모델 모두 1.0000으로 포화**입니다. 프로덕션에서 dense의 임무는 hybrid+
  rerank로 넘길 후보 생성이므로, 이 데이터셋에서는 **본래 임무 기준 세 모델이 동률**이고,
  남은 nDCG 차이는 reranker의 몫입니다.

**② 포맷 ablation — ModelProfile의 가치.** Nemotron FT 모델을 일부러 Qwen 포맷으로 서빙하면:

| Nemotron-1B FT | 전체 | 표준 | 은어 |
|---|---|---|---|
| 올바른 포맷(nemotron3) | 0.8885 | 0.9939 | 0.7879 |
| 틀린 포맷(qwen3) | **0.3452** | 0.5981 | 0.1041 |

168쿼리 중 **138패 1승, p=0.0001**, 그리고 **예외는 하나도 나지 않습니다** — 조용한 실패의
전형입니다. 틀린 포맷의 파인튜닝 모델(0.345)은 **학습조차 안 한 Nemotron base(0.543)보다
못합니다.** 파인튜닝에 쓴 시간이 마이너스가 되는 것으로, 포맷을 한 곳에 강제한 이유입니다.

**③ 서빙 성능 — 실제 Qdrant 경로 측정(`rag-bench`).** 정확도가 동률이면 결정은 비용 축으로
넘어갑니다. 지연시간은 쿼리 1건씩(워밍업 제외) p50/p95/p99로, 자원은 GPU 피크·디스크·저장
발자국으로 측정했습니다 (M2 Pro MPS 기준 — 절대 수치는 서비스 하드웨어에서 재확정 필요):

| | Qwen 0.6B FT | Nemotron 1B FT | Nemotron @1024 |
|---|---|---|---|
| 구조 | 28층 × 1024 | 16층 × 2048 | 16층 × 2048 |
| 응답 p50 / p95 (ms) | 45.8 / 74.5 | **32.9 / 59.1** | 32.5 / 64.4 |
| GPU 피크 | **1,554 MB** | 2,753 MB | 2,753 MB |
| 모델 디스크 | **1.2 GB** | 2.3 GB | 2.3 GB |
| 1M 문서 벡터 저장 | **4.1 GB** | 8.2 GB | **4.1 GB** |
| 색인 처리량 | **8.7 docs/s** | 6.6 docs/s | 6.6 docs/s |
| ANN 근사 손실 | 0.0000 | 0.0000 | 0.0000 |

- **파라미터가 2배인데 응답이 28% 빠릅니다.** 원인은 크기가 아니라 구조입니다 — Qwen은
  깊고(28층) Nemotron은 얕습니다(16층). 배치=1 지연 바운드에선 순차 실행되는 **층수가
  병렬화되는 폭보다 지배적**입니다. **"큰 모델 = 느림"은 단건 응답에서 틀립니다.**
- 대신 **메모리·저장은 정직하게 2배**입니다(GPU 1.8×, 저장 2×, 색인 24% 느림).
- **ANN 손실이 전부 0.0000** — 195문서에선 HNSW가 완전탐색과 동일합니다. 인덱스가 아직
  병목이 아니라는 뜻이며, 이 지표는 실데이터 규모에서 다시 봐야 의미가 생깁니다.

**종합 판단.** 정확도가 유의하게 다르지 않고 recall 임무는 양쪽 다 포화이므로, 결정은
비용 축입니다 — **저장·메모리가 병목이면 Qwen**(절반 비용, 동등 품질), **단건 응답속도가
병목이면 Nemotron**(28% 빠름, 2배 자원). 현재 근거로는 Qwen이 이미 임무를 100% 수행하며
자원을 절반만 쓰므로 **교체 근거가 약합니다.** 단, 이 데이터셋은 두 모델을 변별할 해상도를
소진했고(전부 recall@50=1.0), 지연·메모리는 MPS 수치라 **서비스 하드웨어(CUDA)에서 재측정
시 결론이 달라질 수 있습니다** — 특히 층수 대 폭의 관계는 GPU 커널 특성에 민감합니다.

부산물로 **gradient checkpointing 노브**를 추가했습니다(`TRAIN_GRAD_CHECKPOINT=1`). 1.14B
전체 파인튜닝이 MPS에서 OOM 났을 때, batch·LoRA는 학습 자체를 바꿔 비교를 깨므로 **레시피를
보존하는 유일한 메모리 수단**입니다 — 실측으로 에폭별 결과가 소수점까지 동일함을 확인했습니다.

### 3.7 하이브리드 융합 — dense가 BM25 위에 실제로 얹히나 (7/24)

3.4는 dense와 BM25의 후보 **합집합 recall**로 상보성을 *진단*했습니다(한계 기여 +33%p).
진단은 "천장이 올라간다"는 말이지 실제 순위를 내놓지는 않습니다. 여기서는 두 랭킹을
**Reciprocal Rank Fusion**(RRF)으로 실제 하나로 융합하고 — 점수 스케일이 다른 코사인과
BM25를 순위만으로 섞는 표준 방법 — dense 가중 α 하나를 dev에서 튜닝해, 융합이 각 성분
단독을 이기는지 같은 지표로 쟀습니다(`rag/evaluation/hybrid.py`).

**base·FT × dense·하이브리드 2×2 (dev 168쿼리, nDCG@10 / 은어 슬라이스).**

| | dense 단독 | 튜닝 하이브리드 | dense 대비 |
|---|---|---|---|
| BM25 단독 | — | 0.5687 (은어 0.249) | — |
| **base** (Qwen zero-shot) | 0.5592 (은어 0.152) | 0.5866 (은어 0.201), α=0.7 | +0.028 (p=0.012) |
| **파인튜닝** | 0.8794 (은어 0.772) | **0.9540 (은어 0.918)**, α=0.9 | **+0.075 (p=0.0001, 28승 2패)** |

이 표에서 보고의 두 결론이 나옵니다.

1. **하이브리드는 파인튜닝을 대체하지 못합니다.** base 모델에 BM25를 융합해도 은어는
   0.152 → 0.201로 거의 못 움직입니다 — 은어는 문서 본문에 없으므로 BM25도 못 풀고, base
   dense도 모르므로, 무지한 두 신호를 섞어도 무지합니다. base+하이브리드(0.587)는 파인튜닝
   단독(0.879)에 한참 못 미칩니다. **어휘 융합은 도메인 격차의 지름길이 아닙니다.**
2. **파인튜닝이 선행 조건이고, 하이브리드는 그 위에 얹힙니다.** 큰 융합 이득(0.879 → 0.954)은
   파인튜닝이 은어→시스템을 가르친 *뒤에야* 나옵니다: 그때 BM25의 과업 어휘 신호("지출결의"·
   "OTP 등록")가 dense가 이미 올려둔 정답 문서를 상위로 정렬해 은어 슬라이스 nDCG를
   0.772 → 0.918로 끌어올립니다. dense는 은어를, BM25는 과업 어휘를 알고, 융합이 둘 다 취합니다.

**정직한 한계 — dev 이득이 held-out final에서 재현되지 않았습니다.** α=0.9를 final(54쿼리)에
고정 적용하면 dense 단독(nDCG 0.983)이 이미 천장이라 융합이 오히려 −0.021(p=0.25, 무의미)
입니다. **하이브리드의 이득은 dense에 여지가 있을 때에만 발생**하고, 이미 포화한 슬라이스
에선 중립~소폭 손해입니다 — 하이브리드는 공짜 보편 승리가 아니라 배포처마다 튜닝·확정이
필요한 부품입니다(dev/final 규율이 이 비재현을 그대로 잡아냈습니다). 프로덕션의 형태소
BM25 + 리랭커 조합에서는 절대값이 다르겠지만, "FT가 은어를 열어주고 그 위에서 어휘 융합이
순위를 다듬는다"는 **방향**은 대역 실험이 명확히 보여줍니다.

### 3.8 정성 분석 — 모델이 배운 것을 눈으로 (7/24)

집계 지표(nDCG +0.32)는 "무엇이" 좋아졌는지 말하지 않습니다. 파인튜닝 전후 랭킹을 쿼리
단위로 비교하면, 은어 슬라이스에서 **base가 정답을 1위에 못 올린 쿼리 중 36건이 FT에서
1위 정답으로 뒤집혔고**(23개 시스템에 걸침), 그 실패 양상이 두 가지로 또렷합니다.

| 은어 쿼리 | base의 1위 (오답) | 정답에 대한 base 순위 | 파인튜닝의 1위 (정답) |
|---|---|---|---|
| 파피루스 지출결의 내는 법 | 피플온 사용 가이드 | 3위 | **한결** 사용 가이드 |
| 개미굴 OTP 등록 어디서 해 | 허브포트 사용 가이드 | 9위 | **게이트원** 사용 가이드 |
| 우물 SQL 돌릴 곳 신청 | 타운홀 사용 가이드 | 3위 | **데이터온** 사용 가이드 |
| 솔개 채용 공고 올리기 | 리크루타 — 시스템 소개 | 2위 | 리크루타 **사용 가이드** |
| 자작나무 야근 등록 어디서 해 | 워크로그 **릴리스 노트** | 10위 밖 | 워크로그 **사용 가이드** |
| 감나무 요즘 어디서 봐 | 메일가드 점검·장애 공지 | 10위 밖 | **노트리**(사내 위키) |

- **틀린 시스템**(파피루스→피플온이 아니라 한결, 개미굴→허브포트가 아니라 게이트원): base는
  은어를 모르니 표면적으로 그럴듯한 다른 시스템의 문서를 집습니다. FT는 은어→시스템 매핑을
  배워 정답 시스템으로 갑니다.
- **맞는 시스템·틀린 문서 유형**(솔개·자작나무): 정답 시스템은 맞혀도 "사용 가이드"가 아니라
  "시스템 소개"나 "릴리스 노트"를 1위로 올립니다 — 사용자의 실제 의도(방법을 알려주는 문서)를
  FT가 더 정확히 맞춥니다.

이 사례들은 비ML 이해관계자에게 "모델이 우리 조직의 언어를 배웠다"를 표로 보여주는 자료이며,
보고 페이지에도 실려 있습니다. (추출: 3.4의 저장된 랭킹에서 base r@1=0 → FT r@1=1 필터)

### 3.9 공개 모델 서베이 — 어떤 off-the-shelf 옵션도 은어를 모른다 (7/24)

3.6은 Qwen vs Nemotron 2파전이었습니다. "차기 모델" 결정의 관련연구 근거를 넓히려면 공개
검색 모델의 지형 자체를 봐야 합니다. 서로 다른 계열의 공개 임베딩 모델을 인트라넷 dev 셋에
**zero-shot**(파인튜닝 없이)으로 걸어, 파인튜닝 모델과 같은 표에 놓았습니다. 하니스는 기존
평가 경로를 그대로 쓰고 프로파일만 모델별로(`scripts/model_survey.py`, 결과는 레지스트리에 자동 기록).

| 옵션 (dev 168쿼리) | 계열 | dim | nDCG@10 | recall@50 | 은어 nDCG |
|---|---|---|---|---|---|
| BM25 (문자 bigram) | 어휘 | — | 0.5687 | 0.8274 | 0.2486 |
| KURE-v1 (**한국어 특화**, 공개) | dense | 1024 | 0.5606 | 0.8333 | 0.1931 |
| Qwen3-0.6B (공개) | dense | 1024 | 0.5592 | 0.7262 | 0.152 |
| multilingual-e5-large (공개) | dense·다국어 | 1024 | 0.5521 | 0.7560 | 0.1818 |
| multilingual-e5-base (공개) | dense·다국어 | 768 | 0.5542 | 0.8036 | 0.1579 |
| bge-m3 (공개) | dense·다국어 | 1024 | 0.5439 | 0.8452 | 0.1588 |
| Nemotron-1B (공개) | dense | 2048 | 0.5425 | 0.7440 | 0.1713 |
| **Qwen3-0.6B — 파인튜닝** | dense | 1024 | **0.8794** | **1.0000** | **0.7725** |

- **7종의 공개 옵션(dense 6 + 어휘 1)이 계열 불문 nDCG@10 0.54~0.57에 몰려 있고, 은어는
  전부 0.15~0.25로 붕괴**합니다. 결정적으로, **한국어 특화 모델 KURE-v1조차 은어 nDCG
  0.193으로 참패**합니다(공개 중 최고지만 파인튜닝 0.772의 1/4). 다국어 e5·bge-m3도 마찬가지 —
  **공개 모델의 문제는 "한국어를 아느냐"가 아니라 "우리 조직의 은어를 아느냐"이고, 그 답은 계열·
  한국어 특화 여부와 무관하게 모른다**입니다. 비-FT 옵션 중 최고가 순수 어휘 BM25(0.5687)인 것도
  같은 이유입니다 — 최소한 과업 단어는 문자 일치로 잡으니까(은어는 그마저 안 되지만).
- **파인튜닝 한 번이 이 지형을 벗어나는 유일한 수단**입니다(0.879 / 은어 0.772). 즉 차기 모델
  결정은 "어떤 공개 모델을 그대로 쓸까"가 아니라 **"어떤 base를 파인튜닝할까"**의 문제이고,
  거기서 Qwen과 Nemotron은 동률(3.6)입니다. KURE가 은어에서 근소하게 앞선 것(0.193)은 특화
  base를 파인튜닝 후보에 넣어볼 여지를 시사하나, base 순위가 파인튜닝 후 순위를 예측하지 않음은
  3.6에서 이미 확인됐으므로 zero-shot 우위만으로 선택 근거가 되진 않습니다.

## 4. 리스크와 다음 단계

| 순위 | 과제 | 내용 |
|---|---|---|
| 1 | **실사용 로그 확보** | 파인튜닝 이득의 원천은 실사용 쿼리 분포. 검색창 쿼리 + 클릭 전환 경로를 학습쌍으로 가져오는 경로는 구현 완료 — 데이터 연결만 남음 |
| 2 | **사내 corpus 적용** | 크롤러·파이프라인은 사이트만 바꾸면 동작. 평가 corpus는 지표 포화를 피할 규모(수천 단위)로 설계 |
| 3 | **서빙 벤치 CUDA 재측정** | 3.6의 지연·GPU 수치는 MPS 기준이라 서비스 하드웨어로 이전되지 않음. `rag-bench`는 device-agnostic(CUDA에선 정확한 peak 카운터 자동 사용)이라 서버에서 그대로 재실행하면 결정용 절대 수치 확보. 층수↔폭의 응답속도 관계가 GPU 커널 특성상 뒤집힐 수 있어 특히 필요 |
| 4 | **final 확정 + A/B** | 실데이터에서 dev로 승자 선택 → final 1회 확정 → 프로덕션 hybrid+rerank 조합에서 A/B로 서비스 지표(클릭·이탈) 최종 검증. 랩 점수는 필요조건이지 충분조건이 아님 |
| 5 | **hard negative 고도화** | "비슷해서 틀리는" 쌍(예: 가이드 문서 vs 장애 공지)을 채굴해 Triplet/GIST로 정밀 학습 — 실로그 확보 후 효과가 커지는 항목 |
| 6 | **서베이 실데이터 재확인** | 공개 모델 7종 서베이는 인트라넷 리허설 셋에서 완료(3.9) — 실 corpus로 옮겨 재확인하고, 후보 base를 zero-shot이 아니라 파인튜닝 후 순위로 확정(3.6에서 base 순위≠FT 순위 확인). 하니스·프로파일 완비(`scripts/model_survey.py`, 레지스트리 자동 기록) |
| 7 | **하이브리드 실데이터 확정** | 3.7의 RRF 융합(`rag/evaluation/hybrid.py`)을 프로덕션 형태소 BM25 + 리랭커 위에서 재튜닝·확정. 대역 실험이 보인 "FT가 은어를 열고 → 융합이 과업 어휘로 순위를 정렬" 방향을 실 파이프라인에서 검증. dev/final 규율상 배포처마다 α 재튜닝 필수 |

## 부록 — 이 랩의 숫자를 믿어도 되는 이유 (검증 장치 요약)

| 주장 | 보장 장치 |
|---|---|
| 모든 결과는 재현 가능 | 모델마다 전체 레시피·데이터 지문·epoch별 점수가 train_meta.json으로 자동 기록 |
| 비교는 항상 공정 | 평가셋 지문이 다른 점수끼리는 비교 자체가 차단 |
| "좋은 점수 고르기" 방지 | dev(선택용)/final(확정용) 평가셋 분리, final은 승자 1회만 |
| 차이는 우연이 아님 | 쿼리별 paired 순열 검정으로 p값 제시 |
| 랩 점수 = 서빙 점수 | 임베딩 계약 + 패리티 벡터(cosine ≥ 0.999) 동봉, 서빙 경로에도 동일 포맷 코드 강제 |
| 모델 교체는 무중단 | 재색인 완료 후 alias 원자 전환, 옛 인덱스는 롤백용 보관 |
| 모델별 포맷 오류 차단 | 입력 포맷을 ModelProfile로 한 곳에 정의, 학습·평가·서빙이 동일 참조. 파인튜닝 모델은 base 포맷을 상속하고 런 기록에 사용된 프로파일·차원을 남김 |
| 서빙 성능은 하드웨어별로만 비교 | 벤치 기록마다 하드웨어 지문을 붙이고, 지문이 다른 지연·메모리는 비교 자체를 차단(정확도만 이전) |
